# TESTING_PLAN.md — план емпіричного налаштування фільтрів

Мета: перестати налаштовувати гейти "на око" й почати робити це на основі реальних даних
про те, які показники входу насправді корелюють із виграшними/програшними угодами.

## Метод (узгоджено 2026-07-25)

Не тестуємо фільтри строго по одному послідовно — на мем-коінах це розтяглось би на місяці
(кожен фільтр потребує 20-30 угод для значущості, а фільтрів ~8). Замість цього:

- **Збираємо дані паралельно** по всіх показниках одразу (`entry_signal` тепер логує повний
  знімок входу — commit `74f0403`).
- **Аналізуємо послідовно** — після накопичення вибірки розбираємо кожен показник окремо.

Ключова передумова: щоб показник можна було вивчати, у вибірці має бути **варіативність** по
ньому. Якщо фільтр жорстко відсікає всі "погані" значення, ми ніколи не побачимо, чи вони
справді ведуть до програшу. Тому на час збору три "вигадані на око" пороги послаблено (див.
Фазу 1).

## Фаза 1 — збір даних (АКТИВНА, з 2026-07-25, commit `df150bd`)

Послаблено ТІЛЬКИ три пороги, які були поставлені без даних, щоб у вибірку потрапив ширший
спектр угод:

| Поріг | Було | Стало (тимчасово) |
|---|---|---|
| `max_auto_sniper_count` | 5 | 30 |
| `min_auto_sm_confluence` | 2 | 1 |
| `min_auto_dev_score` | 0.30 | 0.15 |

**НЕ чіпали** (обґрунтовані рішення користувача, не здогадки — лишаються увімкненими):
crowded-блок, ATH-відкат (`min_auto_ath_ratio`=0.6), вимога "dev вийшов", чорний список
повторного входу, всі базові перевірки безпеки (honeypot/rug/податки/mint), ліквідність $3000,
пороги обсягу/угод (вони відсікають токени з порожнім графіком — це шум, не корисні дані).

**Що робимо у Фазі 1:** нічого не міняємо, даємо системі торгувати й накопичувати. Ціль —
~30-50 закритих угод із повним `entry_signal`.

## Фаза 2 — аналіз (коли ~30+ закритих угод)

Розбір: для кожного показника (`sniper_count`, `liquidity`, `vol_1h`, `swaps`, `buy_ratio`,
`ath_ratio`, `age_min`, `chg_5m`, `chg_1h`, `dev_score`, `sm_confluence`, `crowdedness`,
`dev_exited`) рахуємо **вінрейт і середній PnL по бакетах**. Приклад:
- снайпери 0-10 → X% вінрейт, 10-20 → Y%, 20-30 → Z%
- і так по кожному виміру

Виходить чорним по білому: що корелює з виграшем, що ні, що взагалі неважливе. Можливо
виявиться, що снайпери не важливі, а важлива, скажімо, ліквідність чи вік — тоді фокус
зміститься на це.

## Фаза 3 — налаштування по даних

Затягуємо/послаблюємо кожен поріг вже на основі реальних цифр, а не інтуїції. Тільки після
цього кроку "тимчасові" значення Фази 1 перестають бути тимчасовими.

## Опційно (за рішенням користувача)

Якщо після Фази 2 захочемо перевірити й "обґрунтовані" гейти (crowded / ATH-відкат /
dev-вийшов) — послаблюємо їх точково, окремою міні-фазою, а не разом з рештою (щоб не
забруднювати аналіз одразу багатьма змінними).

## Скидання вінрейту більше НЕ видаляє журнал (2026-07-25)

Раніше "скинути статистику" = архів + обнулення `trade_decisions.jsonl` — тобто кожне скидання
знищувало ту саму історію, яку ми збираємо для аналізу. Тепер розділено:
- **Скидання вінрейту** (кнопка "↺ Скинути" в картці статистики, `POST /api/stats/auto/reset`)
  лише ставить "точку відліку" (`outputs/stats_epoch.json`) на поточний момент. Картка показує
  вінрейт тільки від цієї точки. **Журнал не чіпається — жодного запису не видаляється.**
- Уся історія угод із повним `entry_signal` накопичується назавжди, доступна для Фази 2.

**НЕ використовувати старий флоу archive+truncate журналу** — він знищує дані аналізу. Для
"чистого вінрейту з нуля" тепер тільки epoch-скидання.

## Важливо пам'ятати

- Поточні значення 30 / 1 / 0.15 — **тимчасові**, для збору даних. Не сприймати як постійні.
- Оригінальні значення (5 / 2 / 0.30) записані в коментарях CFG (`原值 ...`).
- Захисні фільтри (honeypot/rug/податки) НІКОЛИ не послаблюються заради даних — downside
  катастрофічний і однозначний, там нема чого "вимірювати".
- Послаблювати все одразу не можна — інакше не розбереш, який фільтр вплинув (confounding).
